# Database Migrations — NutriApp Conventions

Full rationale in CLAUDE.md sections 2.5 and 7.

## Tooling
- Alembic, one independent migration history per service (services never
  share a migration history or a schema).
- Autogenerate a draft migration from model changes
  (`alembic revision --autogenerate`), then review and hand-edit it — never
  trust an autogenerated migration blindly, especially around data
  transformations.

## Expand/Contract Pattern (default approach)
For any schema change that could break a running instance of the previous
code version during a rolling deploy:

1. **Expand**: add the new column/table/index as nullable or with a default,
   without removing or renaming anything old. Deploy this first; both old and
   new code can run against this schema.
2. **Migrate data**: backfill the new column/table from the old one, in a
   separate migration, in batches if the table is large (avoid long-held
   locks on a large table).
3. **Contract**: once the new code path is confirmed working and no old code
   is running against this schema anymore, remove the old
   column/table/constraint in a later migration.

Never combine "add new column" and "drop old column" in the same migration/
deploy — that is exactly the non-additive change that breaks zero-downtime
deploys.

## Destructive Changes Require Human Approval
The following require explicit human confirmation before execution, per
CLAUDE.md section 7, and are blocked by `.claude/hooks/pre-bash-guard.sh`:
- `DROP TABLE`, `DROP DATABASE`, `DROP COLUMN`, `TRUNCATE`.
- Any migration that changes a column type in a way that can lose data
  (e.g. narrowing a numeric type, truncating a string column).
- Any migration affecting the audit trail schema (see
  `docs/observability-and-audit.md`).

`devops-agent` authors migrations but never executes a destructive one without
that explicit approval, regardless of how confident it is the change is safe.

## Rollback
Every migration should have a working `downgrade()` implementation where
feasible. For migrations where a clean rollback is impossible (e.g. after a
contract-phase drop), document that explicitly in the migration's docstring
and in the PR description.

## Testing Requirements
- Migrations are tested against a real, containerized Postgres instance
  (`testcontainers`), not mocked.
- For any migration with a data-backfill step, test it against a fixture
  dataset representative of edge cases (nulls, duplicates, boundary values).
- Test both `upgrade()` and `downgrade()` where a rollback path exists.
