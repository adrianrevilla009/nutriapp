# API Conventions — NutriApp

## Routing
- Prefix by service/domain: `/auth`, `/catalog`, `/diary-entries`, `/nutrition`,
  `/vision`, `/analytics`, `/chat`.
- Version in the URL: `/api/v1/...`. A breaking change to a response shape
  requires a new version (`/api/v2/...`), not an in-place change to v1.
- Controllers are thin: parse the request into a DTO, call an application
  layer command/query handler, serialize the result. No business logic in the
  HTTP layer (see `.claude/skills/hexagonal-architecture/SKILL.md`).

## Requests & Responses
- Pydantic v2 models for every request and response — never raw dicts.
- Consistent error shape across all services:
  ```json
  { "error": "human-readable message", "code": "MACHINE_READABLE_CODE" }
  ```
- Pagination is mandatory for any endpoint that can return an unbounded list
  (historical logs, full catalog search results): cursor-based pagination
  preferred over offset-based for stability under concurrent writes.

## Idempotency
- Any endpoint that creates a resource as a side effect of a client retry
  (e.g. the core write action) should accept an optional `Idempotency-Key` header and
  deduplicate on it, to be safe under network retries from the frontend.

## Security
- Every endpoint touching user data requires authentication (a dependency
  validating the token issued by `identity-service`).
- Never return sensitive fields (password hashes, internal tokens) in any
  response, even for admin-facing endpoints.
- Input validation happens at the Pydantic model level, before the request
  reaches the application layer.

## Correlation & Observability
- Every request propagates or generates an `X-Correlation-Id` header,
  threaded through to logs, traces, and any event published as a result of
  handling the request. See
  `.claude/skills/observability-audit/SKILL.md`.

## OpenAPI
- Auto-generated by FastAPI from the Pydantic models and route definitions —
  never hand-maintain a separate OpenAPI spec that can drift from the code.
- Every endpoint has a `summary` and `description` populated (used directly in
  the generated docs).

## Testing
- Every endpoint has at least one contract test (happy path against its
  documented OpenAPI schema) and one error-path test.
- See `docs/testing-strategy.md` for the full testing pyramid this fits into.
