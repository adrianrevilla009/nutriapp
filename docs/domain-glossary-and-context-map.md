# Domain Glossary & Bounded Context Map

Standard DDD artifacts: a shared vocabulary (ubiquitous language) and an
explicit map of how NutriApp's 14 bounded contexts (CLAUDE.md section 2.2)
relate to each other. An agent implementing any service should read this
document first to know the exact meaning of a term before writing a single
entity or event name that uses it.

## 1. Domain Glossary (Ubiquitous Language)

| Term | Definition | Owning bounded context |
|---|---|---|
| User | An individual authenticated principal. NutriApp is single-tenant (ADR-0018) — there is no Tenant/Organization concept above a User. | `identity-service` |
| Food Entry | A single logged instance of food eaten: a product/recipe/photo-detected item, a quantity, a meal slot, and a timestamp. | `diary-service` |
| Water Intake Entry | A single logged instance of water consumed. | `diary-service` |
| Fasting Window | A recorded start/end interval of an intermittent-fasting period. | `diary-service` |
| Meal Plan Entry | A food entry scheduled ahead of time, distinct from an as-eaten Food Entry. | `diary-service` |
| Product | An item in the supermarket product inventory: name, brand, barcode, per-100g nutrition data, dietary/allergen tags. | `catalog-service` |
| Dedup Key | The identity `catalog-service` uses to decide whether an incoming, normalized source record is the same Product as one already catalogued: barcode when present (the sole cross-source key — no fuzzy name+brand matching), otherwise `(source, source_product_id)` scoped to that one source only. | `catalog-service` |
| Ingestion Run | One bounded execution of a `catalog-service` source adapter over a page/batch of records, audited (source, started/finished timestamps, items seen/added/updated/skipped, status) independent of any other source's run — one source's failure never blocks another's. | `catalog-service` |
| Nutrient Total | The computed macro/micronutrient sum for a Food Entry, a meal, or a day. `recipe-service` computes its own analogous per-recipe/per-serving Nutrient Total for a Recipe, via its own independent copy of the same per-100g x quantity formula (CLAUDE.md section 2.5 forbids the cross-service code import; anti-drift guarded by the shared `packages/shared-contracts/fixtures/nutrient_calculation_reference_cases.json` reference fixture both services' tests may consume) — not the same computed value or type as this row's own. | `nutrition-calculation-service` (Food Entry/meal/day); `recipe-service` (Recipe, own copy) |
| Nutrition Target | The computed calorie/macro goal for a user, derived from Profile metrics and Goal via the Mifflin-St Jeor formula. | `nutrition-calculation-service` |
| Profile Metric | A single biometric reading (weight, height, age, sex, activity level). | `profile-service` |
| Biometric Consent | A user's explicit, specific grant of consent to collect biometric/health data (CLAUDE.md section 8) — distinct from, and never bundled into, general ToS acceptance. Required before any Profile Metric or Goal can be recorded; recorded as its own event (`BiometricConsentGranted`), not a flag bundled into another record. | `profile-service` |
| Goal | A user's stated objective (lose/maintain/gain weight, target value/date) used as a Nutrition Target input. | `profile-service` |
| Detection | A food-recognition-service result from a photo or barcode scan: an identified item, a confidence range, and (for photos) an estimated nutrient range — always subject to user confirmation before becoming a Food Entry. | `food-recognition-service` |
| Exercise Entry | A manually logged bout of exercise with a user-supplied calorie-burn estimate (exercise type, duration, calories burned, occurred-at). Wearable-synced entries are a documented, not-yet-built future addition — see `services/activity-service/README.md`. | `activity-service` |
| Wearable Provider | A third-party fitness-tracking platform (Apple Health, Google Fit, Fitbit, Garmin) `activity-service` could sync activity data from via `WearableProviderPort`. Interface-only in this MVP — zero adapters implemented, pending developer account registration per provider (`docs/vendor-risk-register.md`). | `activity-service` |
| Recipe | A user-authored combination of Products with quantities, servings, and a computed per-serving Nutrient Total. | `recipe-service` |
| Publish (a Recipe) | Making a Recipe visible in cross-user Recipe search — a Pro-gated action, distinct from authoring a Recipe for personal use. Blocks if any ingredient no longer resolves to a real `catalog-service` product, re-verified fresh at publish time. Un-publishing/deleting is always a soft-unpublish (never a hard row delete); publishes `RecipeUnpublished`. | `recipe-service` |
| Follow | A one-way connection from one User to another (this User sees that User's public activity). Not an organizational membership — see `docs/multi-tenancy.md`. | `social-service` |
| Subscription | A User's Pro-tier billing state (active/cancelled/past-due) and its renewal cycle. | `billing-service` |
| Entitlement | A derived flag (from Subscription state) that a Pro-gated service checks before serving a Pro feature (recipe publish/search, following, reports, data export). | `billing-service` (issued), consumed by `recipe-service`, `social-service`, `analytics-service` |
| Anomaly | A detected recurring pattern over a rolling window (e.g. a sustained micronutrient deficiency) surfaced to the user or the assistant. | `analytics-service` |

## 2. Bounded Context Map

Document the relationship type between each pair of bounded contexts that
communicate, using standard DDD context-mapping patterns. Not every pair
needs a relationship — only document ones that actually integrate.

| Upstream context | Downstream context | Relationship pattern | Notes |
|---|---|---|---|
| `identity-service` | every other service | **Shared Kernel** (the `user_id` identity concept) via **Open Host Service** (JWT claims validated at Kong) | `identity-service` never changes the token contract without an ADR (`docs/authorization-model.md`) |
| `identity-service` | `profile-service` | **Customer-Supplier** via published events | `profile-service` creates a profile in reaction to `UserRegistered`; it does not call `identity-service` synchronously |
| `notification-service` | `identity-service` | **Conformist**, narrow synchronous exception | `notification-service` (built -- `/plans/notification-service/implementation-plan.md`) calls `POST /internal/v1/auth/tokens/{reference_id}/reveal` once per email-verification/password-reset flow to retrieve a raw secret (identity-service plan §5, "reference+secret" pattern) — never routed through Kong, authenticated via identity-service's single shared `internal-reveal-credential` (`infrastructure/external/identity_token_reveal_client.py`, its own dedicated circuit breaker). This is a deliberate, single-endpoint exception to `identity-service`'s Open Host Service relationship with every other service above, not a general precedent for synchronous calls into `identity-service` |
| `notification-service` | `diary-service` | **Customer-Supplier** via published events | `notification-service` is a pure consumer of `FastingWindowStarted`/`Ended`, `MealPlanned`/`Updated`/`Removed`, `WaterIntakeLogged`/`Removed` (projected into its own local `reminder_schedule` read model, then scanned by an in-service periodic worker) — never a synchronous call into `diary-service`; `diary-service` is not obligated to conform to `notification-service`'s roadmap |
| `catalog-service` | `diary-service` | **Customer-Supplier** | `diary-service` consumes catalog data as a customer; `catalog-service`'s roadmap is influenced by what `diary-service` needs, but is not obligated to conform |
| `catalog-service` | `recipe-service` | **Open Host Service** (already-public API, called server-to-server) | `recipe-service` (built -- `/plans/recipe-service/implementation-plan.md`) calls catalog-service's existing PUBLIC `GET /api/v1/catalog/products/{id}` endpoint (own `catalog_product_lookup` circuit breaker) to resolve each recipe ingredient's nutrition data at create/update time, and to re-verify every ingredient still resolves fresh at publish time (never trusted from creation time — recipe-agent.md). Same Open Host Service classification/rationale as the `diary-service`->`bff-service` row below, not the internal-reveal-endpoint exception pattern — no new endpoint was added to `catalog-service` for this. Corrected from an earlier speculative "Customer-Supplier" placeholder now that the integration is actually built |
| `recipe-service` | `analytics-service`, `nutrition-assistant-service` | **Customer-Supplier** via published domain events (documented, not yet wired) | `recipe-service` publishes `RecipeCreated`/`RecipeUpdated`/`RecipePublished`/`RecipeUnpublished` on every corresponding lifecycle action. Neither consuming service exists yet — same deferral shape as `activity-service`->`nutrition-calculation-service`'s `ExerciseLogged` row above |
| `recipe-service` | `social-service` | **Customer-Supplier** via published domain events | `social-service` (built -- `/plans/social-service/implementation-plan.md`) is the FIRST real consumer of `RecipePublished`/`RecipeUnpublished`: projects a local `feed_entries` read table (fan-out-on-read) for `GET /api/v1/social/feed`, never a synchronous call into `recipe-service` and never a duplicate of its write model (CLAUDE.md section 2.5). `recipe-service`'s roadmap is not obligated to conform to `social-service`'s needs — a known gap is `RecipePublished`'s payload not carrying a `title` field `social-service`'s feed listing would want, deferred to a possible future v2 rather than reopening the already-merged `recipe-service` for this plan |
| `diary-service` | `nutrition-calculation-service` | **Customer-Supplier** via published domain events | `nutrition-calculation-service` reacts to `diary-service`'s events; it does not call back synchronously (CLAUDE.md section 2.2) |
| `profile-service` | `nutrition-calculation-service` | **Customer-Supplier**, published domain events as trigger + a narrow synchronous exception | `WeightRecorded`/`BodyMetricRecorded`/`GoalSet`/`GoalUpdated` trigger target recomputation, but carry only ciphertext (ADR-0023) -- `nutrition-calculation-service` never decrypts them itself. It instead calls `POST /internal/v1/profile/{user_id}/reveal-metrics` synchronously (circuit-breaker + retry, own dedicated breaker never shared with `profile-service`'s internal KMS breaker) to obtain plaintext metrics, per an approach directly analogous to `notification-service` -> `identity-service`'s reveal-endpoint exception above -- a deliberate, single-endpoint exception to `profile-service`'s otherwise pure event-published relationship with its consumers, not a general precedent for synchronous calls into `profile-service` (implementation plan Addendum 1) |
| `activity-service` | `nutrition-calculation-service` | **Customer-Supplier** via published domain events (documented, not yet wired) | `activity-service` (built -- `/plans/activity-service/implementation-plan.md`) publishes `ExerciseLogged` on every manual log/correction. `nutrition-calculation-service`'s `NutritionTargetUpdated.activity_adjustment_kcal` field is reserved for this but always `null` this pass -- wiring a real consumer means reopening that already-merged, already-closed service's formula surface, gated behind a new ADR per its own `CLAUDE.md`. Same deferral shape as `analytics-service` -> `NutrientDeficiencyDetected` elsewhere in this table |
| Any Wearable Provider | `activity-service` | **Anticorruption Layer** (planned, not yet built) | `WearableProviderPort` (`connect`/`sync`/`disconnect`) is the seam a future adapter for Apple Health/Google Fit/Fitbit/Garmin would implement, translating each provider's own API/OAuth shape into `activity-service`'s domain vocabulary. Zero adapters exist yet -- no real developer-account credentials are registered for any of the four providers (`docs/vendor-risk-register.md`) |
| `food-recognition-service` | `diary-service` | **Anticorruption Layer** | External vision-provider concepts (confidence scores, provider-specific labels) are translated into `diary-service`'s own domain vocabulary at the `food-recognition-service` boundary — `diary-service` never sees a provider-specific type |
| `food-recognition-service` | `catalog-service` | **Customer-Supplier** | Barcode detections are looked up against catalog product data |
| `billing-service` | `recipe-service`, `social-service`, `analytics-service` | **Open Host Service** (entitlement events + a fallback sync check) | `recipe-service` (built -- `/plans/recipe-service/implementation-plan.md`) is the FIRST real consumer, and `social-service` (built -- `/plans/social-service/implementation-plan.md`) is the SECOND: each caches the entitlement flag locally in its own `entitlement_cache` table (populated by consuming `EntitlementGranted`/`EntitlementRevoked`) per `.claude/skills/saga-conventions/SKILL.md`, checked before its own Pro-gated actions (`recipe-service`: `publish`/`search`; `social-service`: `follow`/`unfollow`/`feed`); a cache miss falls back to `GET /internal/v1/billing/entitlements/{user_id}` (own, independently-named `billing_entitlement_check` circuit breaker per service, never sharing state across services or with `catalog_product_lookup` above) — a narrow synchronous exception, same **Conformist** classification precedent as the other internal-endpoint consumers (`notification-service`->`identity-service`, `nutrition-calculation-service`->`profile-service`). A lagging or absent consumer fails safe (not-yet-entitled), never fail-open. `analytics-service` remains a documented, not-yet-implemented consumer (that service doesn't exist yet) |
| `social-service` | `notification-service` | **Customer-Supplier** via published domain events | `social-service` publishes `UserFollowed` on every new follow (never on an idempotent repeat); `notification-service` (already-merged, gains a real `social_events_consumer.py` per this initiative's coordinated PR A) dispatches an opt-in, suppressible `new_follower` push notification. `UserUnfollowed` is NOT consumed by `notification-service` -- unfollowing does not notify the formerly-followed user (implementation plan section 1.5) |
| `nutrition-assistant-service` | `diary-service`, `profile-service`, `nutrition-calculation-service`, `analytics-service` | **Conformist** | The assistant's retrieval layer conforms to the read models these services already publish, rather than requesting new integration points |
| `analytics-service` | `notification-service` | **Customer-Supplier** via published events | `analytics-service` decides an alert is warranted (`NutrientDeficiencyDetected`); `notification-service` only delivers it |
| `diary-service` | `bff-service` | **Open Host Service** (already-public API, called server-to-server) | `bff-service` (built -- `/plans/bff-service/implementation-plan.md`) calls diary-service's existing PUBLIC `GET /api/v1/diary/summary?date={date}` endpoint to build its dashboard aggregation, forwarding the caller's own `Authorization` header unchanged. Explicitly distinct from the internal-reveal-endpoint exception pattern (`identity-service`->`notification-service`, `profile-service`->`nutrition-calculation-service`, `catalog-service`->`food-recognition-service` rows above): those exist because the data needed wasn't safely exposable on a public endpoint; here `bff-service` calls the exact same public, Kong-routable surface the frontend would otherwise call directly, purely to do the fan-out/composition the frontend would otherwise do itself in three separate requests. No new endpoint was added to `diary-service` for this |
| `nutrition-calculation-service` | `bff-service` | **Open Host Service** (already-public API, called server-to-server), two independent calls | `bff-service` calls nutrition-calculation-service's existing PUBLIC `GET /api/v1/nutrition/totals/{date}` and `GET /api/v1/nutrition/target` endpoints in parallel, each behind its own independently named circuit breaker despite sharing a host (`.claude/skills/resilience-patterns/SKILL.md`). Same Open Host Service classification and rationale as the `diary-service` row above -- not the internal-reveal-endpoint exception pattern. `GET /api/v1/nutrition/target`'s documented `Sex.OTHER`/deferred-recompute gap (`services/nutrition-calculation-service/README.md`) surfaces to `bff-service` as a well-formed `404`, mapped to an explicit `not_yet_computed` section status, never synthesized or guessed |
| Any external third-party API (payment processor, vision/LLM provider, wearable provider) | the owning service | **Anticorruption Layer** | Per `.claude/skills/resilience-patterns/SKILL.md` — the port abstraction (e.g. `RecognitionPort`, `WearableProviderPort`, `PaymentProviderPort`) already enforces this at the code level; this row makes the DDD pattern name explicit |

## 3. How This Interacts with Section 2.2's Service Table

CLAUDE.md section 2.2 lists bounded contexts by their technical shape
(one service, one database). This document adds the *semantic*
relationships between them — which context's model is authoritative for
a shared concept, and which context has to adapt to the other. When the
two disagree (e.g. a service table entry implies two contexts are more
tightly coupled than their actual relationship pattern here suggests),
this document is the tiebreaker for architectural review, since it
reflects deliberate DDD analysis rather than just a service inventory.

## 4. Maintenance

Update this document in the same pull request that introduces a new
bounded context, a new cross-context integration, or a term whose meaning
would otherwise be ambiguous across two services. `architecture-agent`
checks new entity/event names against the glossary during
`/implementation-review` and flags any term used with a meaning that
doesn't match its glossary entry (or any new domain term introduced
without being added here).
